## Decisions applied on 18 Oct 2026

- **Removed from the plan:** the supervisor meeting, the ADR update after the meeting, the `pre-defense-1` tag, and the `pre-defense-2` and `final-pre-defense` tags. Note: section 13 of the proposal still lists the `pre-defense-1` tag as a deliverable for 24 Oct, and the items that needed supervisor confirmation (pilot size, numeric targets, EQ1 coverage) now have no task to settle them. They are listed in section 5 as open points.
- **Plain PostgreSQL, no pgvector.** There are no embeddings. Knowledge chunks are text rows with a `tsvector` index. Retrieval (T-35) is hybrid: the question is parsed into programme and requirement type and the matching Verified records are fetched by SQL; PostgreSQL full-text search (`ts_rank`, `pg_trgm` for typos) is the fallback. The status filter lives inside the SQL query, so a non-Verified record cannot be returned. Trade-off: weaker on paraphrased questions than semantic search, and PostgreSQL has no Kazakh text-search configuration (Russian and English exist). Measure retrieval recall on the 60-question set (T-36); if it is too low, pgvector can be added later without changing the schema contract. This differs from the proposal text (sections 3.5, 7.1, 7.5 and Decision 2 still mention pgvector and embeddings); the technology comparison task in youtrack-tasks.csv aligns README and ADR-0001, and the proposal wording and the ERD note on embeddings should be updated.
- **No ORM (no SQLAlchemy, no Alembic).** The backend talks to PostgreSQL through psycopg 3 and a thin repository layer that returns typed Pydantic models. Schema changes are versioned plain `.sql` migrations with up and down parts, applied by dbmate (can be swapped for another SQL migration runner; the choice is not fixed by the proposal). Costs: relations and row mapping are written by hand and migrations are not autogenerated; benefit: every query, constraint and full-text search is plain, reviewable SQL. The rule engine, status life cycle and roadmap generator stay pure Python modules without database access. Affects the database layer item and the proposal's section 5 stack line (SQLAlchemy and Alembic).

## 1. Ordering principles

1. **Trust model first.** The data model with source, status and validity (C1) and the status life cycle come before any feature that reads requirements. Matching, roadmap and advisor all depend on it.
2. **Deterministic core before AI.** Matching and roadmap do not need an LLM, so they can be built and tested while the AI layer is still being prepared.
3. **Contract first, then parallel work.** The API contract (T-04) is agreed before Artur's backend/frontend and Dinara's AI work diverge. Screens are built against stubs.
4. **Data early.** The pilot dataset (20 programmes in Kazakhstan and the United States) is the slowest manual work and is needed by both evaluation and advisor, so entry starts in S2 and is frozen at the end of S3.
5. **Tests with the feature.** Each core module gets its tests in the same sprint, because Must acceptance criteria are test-based (FR-02, FR-08, FR-09, FR-10, NFR-03, NFR-05).
6. **Evaluation last, but prepared early.** Gold cases (T-33) and the 60-question AI set (T-36) are written in S3, before the code they test is finished.

## 6. Gaps found in the proposal (decide with the supervisor)

1. **EQ1 has no requirement.** EQ1 evaluates programme recommendations (Precision@5 against a keyword filter), but FR-04 only requires a catalog with filters. T-53 (eligibility-first ranking) is planned as Should until a requirement is added or EQ1 is dropped.
2. **Account deletion is Must (NFR-02) but has no task in the proposal's journey.** Added as T-65.
3. **README vs proposal scope.** The README task in youtrack-tasks.csv fixes it; mentor/supervisor dashboards stay Won't.
4. **Language.** No requirement states interface languages. Admission data and the Kazakhstan context suggest Russian and Kazakh, but the proposal lists limited multilingual capability as a chatbot risk [7]. Plan assumes English UI first with i18n-ready structure; confirm.
5. **LLM provider and hosting** are not named. They are dependencies in section 10.4 and block T-19 and T-77.
6. **Numeric targets** (85% extraction, 95% accuracy, 2% false Met, SUS 70, 60 questions) are labelled proposals; tasks reference them but do not fix them.
7. **Pilot size.** The latest proposal says 20 programmes in Kazakhstan and the United States (O2, D2, section 9.4), but the sentence in section 1.6 about the change of size is garbled and earlier versions proposed 10. The plan assumes 20 (10 per member), about 160 requirement records with Tier 1 sources and a second check on each; this is the largest manual job in the project, so confirm that it is realistic.
8. **Proposal says pgvector.** Sections 3.5, 7.1, 7.5 and Decision 2 of section 5 mention pgvector and embeddings; reword them for plain PostgreSQL with full-text search, psycopg 3 and SQL migrations.
9. **Eligibility outcomes.** O4 and section 1.7 use three states (Meets, Action needed, Unknown); FR-08, section 3.3, 6.3 and the activity diagram use four (Met, Not met, Pending, Unknown). The plan uses the four-state version; the proposal must be made consistent.
